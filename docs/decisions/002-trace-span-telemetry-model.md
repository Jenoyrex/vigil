# 2. Trace & Span Telemetry Model

- Status: Accepted
- Date: 2026-08-29

## Context

Vigil's core product surface is ingesting telemetry from AI applications instrumented with its
SDKs. A trace represents one complete execution of an AI application workflow; a trace contains
many spans, each representing one operation within it (an LLM call, a retrieval, a tool call, an
embedding generation, a database query, an agent step, or a plain application function), and spans
form a tree via parent/child relationships.

Per the existing architecture (ADR 001), this telemetry will eventually be stored in ClickHouse,
which is well suited to high-volume, append-heavy, analytical event data, while PostgreSQL
continues to store low-volume relational/application metadata (users, organizations, projects, API
keys, as established in ADR 001 and the PostgreSQL foundation). Before implementing ingestion or
storage, the telemetry data contract and storage model need to be settled, because they determine
the SDK wire format, the storage engine's schema, and how tenant isolation and idempotency are
enforced for a very different write pattern than the existing relational data.

This ADR does not create ClickHouse configuration, tables, or migrations, modify application code
or existing database models, add dependencies, or implement the ingestion API, OpenTelemetry
support, or Redis. It documents the approved design only; implementation is separate, later work.

## Decision

1. **A Trace is a derived logical grouping of spans, not an independently ingested entity.** The
   SDK only ever sends spans. A trace is the set of all spans sharing a `trace_id`; trace-level
   fields (start time, duration, status, root span, environment, release) are derived from that
   span set, not stored as an authoritative, independently-mutated row. In ClickHouse this
   derivation is maintained incrementally by a materialized view (e.g. `traces`) keyed on
   `trace_id`, triggered on span insert, rather than computed from a full scan on every read.

2. **Span model.** Each span row carries: identity/tree fields (`span_id`, `trace_id`,
   `parent_span_id`, `project_id`); naming/typing (`name`, `span_type`, `resource`); timing
   (`start_time`, `end_time`, derived `duration_ms`); status (`status`, `status_message`); content
   (`input`, `output`, `attributes`, `events`); first-class LLM fast-path columns (`llm_provider`,
   `llm_model`, `llm_input_tokens`, `llm_output_tokens`, `llm_total_tokens`, `llm_cost_usd`);
   promoted cross-type filter dimensions (`environment`, `release`); and an `ingested_at`
   server-receipt timestamp distinct from client-supplied event time. Type-specific fields beyond
   the LLM fast-path (retrieval query/results/scores, tool name/input/output, request parameters)
   live in the generic `attributes` bag under a documented, namespaced key convention (e.g.
   `retrieval.query`, `tool.name`, `llm.request.temperature`), not as dedicated columns. `project_id`
   is denormalized onto every span (not derived via a join through trace) so every read query can
   filter/partition on tenant directly.

3. **Ingestion envelope.** A single endpoint and payload shape serves both "send a complete
   finished trace" and "spans arriving independently, batched, and out of order":

   ```
   POST /v1/traces
   Authorization: Bearer <api_key>

   {
     "resource": { "sdk.name": "...", "sdk.version": "...", "service.name": "..." },
     "spans": [ { "trace_id": "...", "span_id": "...", "parent_span_id": null, ... }, ... ]
   }
   ```

   A batch's `spans` array may contain one or many spans, and need not share a single `trace_id` —
   an SDK flushing periodically will typically batch spans from several concurrent traces
   together. `resource` is shared across all spans in the batch, matching OpenTelemetry's
   `ResourceSpans` shape. No separate "trace" object or endpoint exists; sending a whole finished
   trace in one call is simply the case where a batch happens to contain every span for one
   `trace_id`.

4. **IDs are OpenTelemetry/W3C-compatible, not proprietary.** `trace_id` is a 128-bit value,
   hex-encoded as 32 characters; `span_id` is a 64-bit value, hex-encoded as 16 characters — the
   same format used by the W3C Trace Context header and every OpenTelemetry-instrumented library.
   `project_id` remains the existing PostgreSQL `uuid`, resolved server-side from the
   authenticated API key rather than generated by telemetry tooling.

5. **`span_type` is an open, unconstrained string**, not a database-enforced enum or CHECK
   constraint. It is stored as `LowCardinality(String)` in ClickHouse for query efficiency, with a
   documented recommended vocabulary (`llm`, `retrieval`, `embedding`, `tool`, `function`, `agent`,
   `db`, `http`, `unknown`) enforced only at the application/SDK layer, not the database — new span
   kinds must not require a schema migration to be ingested.

6. **Span status follows OpenTelemetry's three-value model**: `unset` (default), `ok`, `error`,
   with a separate `status_message` for detail (e.g. exception text). Trace status is derived, not
   independently settable: `error` if any span in the trace has `status = error`; else `ok` once
   the root span (the span with `parent_span_id IS NULL`) has arrived with a non-null `end_time`;
   else `unknown` (still in progress or missing its root span). There is no explicit
   "trace completed" signal in V1 — completion is inferred from root-span arrival.

7. **Idempotency key is `(project_id, trace_id, span_id)`**, valid because V1 spans are ingested
   only once, as complete immutable units — there is no incremental start/end update to an
   existing `span_id`. Deduplication is implemented via ClickHouse's `ReplacingMergeTree` engine,
   which asynchronously discards duplicate-key rows (e.g. from HTTP retries) during background
   merges. This deduplication is eventual, not immediate: a query run immediately after a retried
   insert may transiently see duplicate rows until the next merge; read paths that need immediate
   correctness (e.g. a single trace detail view) should use `FINAL` or `LIMIT 1 BY` explicitly.

8. **Storage boundary**: PostgreSQL continues to hold `users`, `organizations`,
   `organization_memberships`, `projects`, and `api_keys` — low-volume, mutable,
   relational-integrity-critical data accessed via point lookups and small joins, requiring strong
   ACID consistency (unchanged from ADR 001 and the PostgreSQL foundation). ClickHouse will hold
   `spans` and the derived `traces` rollup — high-volume, append-only, time-ranged/aggregated
   telemetry. The two stores are joined only at the application layer (an ingestion request
   resolves its API key to a `project_id` from PostgreSQL once; span rows carry `project_id`
   denormalized so the trace/span explorer never needs a live cross-database join to render).

9. **Proposed ClickHouse partitioning/ordering** (for implementation when the ClickHouse schema is
   built): `PARTITION BY toYYYYMM(start_time)` (event-time monthly partitions, enabling cheap
   partition-drop retention and time-range pruning); `ORDER BY (project_id, toDate(start_time),
   trace_id, span_id)` (tenant first for isolation and partition/granule pruning, date next for
   time-range pruning, `trace_id` next so all spans of one trace are physically colocated for fast
   single-trace reads, `span_id` last for uniqueness); TTL-based retention
   (`TTL start_time + INTERVAL N DAY DELETE`) aligned to the monthly partitions so expiry is a
   cheap partition drop rather than a row-level `DELETE`.

10. **Privacy/security posture for V1**: no automatic PII/secret redaction is implemented — `input`
    and `output` are the highest-risk fields (may contain end-user PII, business data, or leaked
    secrets) and are deliberately nullable/omittable so a customer can send only token counts and
    metadata if required, and are structurally isolated from `attributes` so a future redaction
    pass can target them specifically. Ingestion must enforce a maximum payload size per span
    (with explicit truncation and a truncation marker, not silent drop) to bound worst-case
    storage/cost exposure. `project_id` must always be derived server-side from the authenticated
    API key and never accepted from the request payload, preventing cross-tenant span injection.
    Read-side access control mirrors the PostgreSQL organization-membership model: every telemetry
    query is scoped to the requesting user's authorized `project_id` set at the application layer,
    since ClickHouse has no equivalent to PostgreSQL row-level security.

## Reasoning

- Deriving traces from spans rather than ingesting them as a separate entity avoids reconciling
  partial/inconsistent trace state across independent, possibly out-of-order span arrivals, and
  avoids fighting ClickHouse's weak mutation support (`ALTER TABLE UPDATE` is heavyweight) with a
  row that would otherwise need patching on every new span.
- A single ingestion envelope for both "complete trace" and "independent/out-of-order spans"
  avoids building and maintaining two API shapes for what is, from the server's perspective, the
  same operation: appending some spans.
- Promoting only a small set of fields (LLM usage/cost, environment, release) to first-class
  columns — instead of a fully generic attributes-only schema — keeps the product's highest-value
  queries (token usage, cost, model breakdowns, environment/release filtering) fast on ClickHouse's
  columnar engine, while the generic `attributes` bag preserves flexibility for the long tail of
  type-specific and future fields without schema churn.
- OpenTelemetry-format IDs cost nothing to adopt now (equivalent effort to generating a UUID) and
  give free interoperability with any OpenTelemetry-instrumented tooling a customer already runs,
  satisfying the requirement to prefer an established standard over a proprietary format.
- An open `span_type` string, rather than a closed enum, matches the fact that new span kinds will
  keep appearing as Vigil covers more of the AI stack, and a schema migration should not gate
  ingesting a new kind of operation.
- OpenTelemetry's three-value status model is adopted directly rather than inventing a Vigil-specific
  status vocabulary, for the same interoperability reason as the ID formats.
- `ReplacingMergeTree`-based deduplication avoids introducing new infrastructure (e.g. a Redis-backed
  exactly-once cache) for idempotency, consistent with ADR 001's decision to defer Redis until a
  feature actually requires it.
- The proposed partition/order strategy puts `project_id` first for the same reason PostgreSQL's
  row-level security design scopes every query by organization: tenant isolation must be enforced
  on every single read, so the tenant key belongs at the front of whatever index structure exists.

## Tradeoffs

- Deriving traces from spans means "is this trace complete" is a heuristic (root-span arrival), not
  a fact, until an explicit completion signal is added — a trace that never receives its root span
  (e.g. dropped by a network error) will appear perpetually in-progress.
- The hybrid schema (LLM fast-path columns + generic attributes) couples the span schema visibly to
  "LLM observability is the primary use case"; other span types (retrieval, tool) may need their own
  fast-path columns later if they prove equally query-hot, which will be a schema change at that
  point.
- An open `span_type` string gets no database-level validation; typos or unrecognized types are
  only caught at the application/dashboard layer.
- OpenTelemetry-format trace/span IDs are a different "shape" from the UUIDs used everywhere else
  in the platform (PostgreSQL primary keys) — contributors must know trace_id/span_id are not UUIDs
  and should not be stored in a PostgreSQL `uuid` column.
- `ReplacingMergeTree` deduplication is only eventually consistent; read paths that need immediate
  per-trace correctness must explicitly account for this (`FINAL`/`LIMIT BY`), and broad analytics
  must tolerate brief, self-correcting overcounting after retried inserts.
- Restricting V1 to complete, immutable spans (no incremental start/end updates to one `span_id`)
  simplifies storage and idempotency significantly, but defers true streaming ingestion — a
  dashboard cannot show "this LLM call is still in progress" live; the SDK must buffer client-side
  until a span finishes.
- No redaction is implemented in V1; raw prompts/responses are stored as sent, bounded only by a
  payload-size cap. This is an accepted, explicit gap for this stage, not an oversight.

## Consequences

- Implementation of the ClickHouse `spans` table and `traces` materialized view must follow the
  field set, partitioning (`PARTITION BY toYYYYMM(start_time)`), ordering
  (`ORDER BY (project_id, toDate(start_time), trace_id, span_id)`), and `ReplacingMergeTree`
  engine choice documented here, unless a follow-up ADR revises them.
- The ingestion API implementation must derive `project_id` from the authenticated API key and
  must reject or ignore any client-supplied `project_id` in the request body.
- SDK implementations (Python and TypeScript) must generate OpenTelemetry-format `trace_id`/
  `span_id` values and buffer spans client-side until they are complete before sending them, per
  the V1 "complete spans only" decision.
- Any new span-type-specific field that becomes a hot query/aggregation target should prompt a
  revisit of decision 2 (adding it as a first-class column) rather than leaving it in `attributes`
  indefinitely, mirroring the same principle ADR 001 established for a future shared core package.
- Redaction, API-key authentication enforcement, OTLP-compatible ingestion, and per-plan retention
  tiers remain open and are intentionally out of scope for this ADR; each should be recorded in its
  own follow-up ADR when implemented.
